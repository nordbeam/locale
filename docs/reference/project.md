# Project generation — `nordbeam-locale/project`

Project APIs read catalogs and own generated output on disk. The package root,
`nordbeam-locale`, exports the same API.

```ts
import { generate, check, createGenerator } from 'nordbeam-locale/project';
```

- `GenerateOptions` and `GenerateResult` — generation input and result types.
- `generate(options)` — read, compile, and write generated modules.
- `writeProject(project, directory)` — write a compiled project.
- `check(options)` — validate the configured project without writing.
- `createGenerator(options, cacheOptions?)` — make a repeatable generator for
  watch integrations.
- `updateCatalogText(text, changes)` — pure formatting-preserving catalog text
  updates; it does not read or write files.

Use `nordbeam-locale/project` for file-backed generation and checks. Keep
in-memory contract comparison and text updates in the compiler/project APIs so
cloud workers do not need filesystem access.

## Generated output

Every generated file names its build mode and where to edit. The first line is
`// Generated by Nordbeam Locale (development|production build). Do not edit:
change <catalogs>/*.json and run \`nordbeam-locale\`.` (on `.js` files it is the
second line, after `// @ts-nocheck`). The line is rewritten in place, so
declaration maps keep their line numbers. `writeProject` writes the compiler's
header unchanged; `generate` applies the marker.

The ownership manifest, `.nordbeam-locale-manifest.json`, records what the last
generation depended on:

- `inputs`: a digest of the compiler fingerprint, the effective options and each
  catalog's bytes, with the per-part hashes that explain a change.
- `outputs`: each generated file's content hash, size and mtime.
- `project`: locales, groups and warnings, so a no-op run can return the same
  result without compiling.

`generate` skips compilation and writes when the input digest matches and every
output still matches its recorded stat, or its content hash when the stat has
changed. A verified no-op returns the same `files`; their contents are read from
disk on first access. An old manifest without `inputs` is ignored and rewritten.

`persistentCache` stores the compiled project keyed by the same input digest.
A hit restores through the normal output path, so missing or modified files
are rewritten from the cache without compiling. The envelope is a header line
(version, key, payload length) followed by the JSON payload. A hit does not hash
the payload, so a same-length edit that keeps the payload valid JSON is not
detected at restore; delete the cache directory to clear it.
