# Nordbeam Locale

Nordbeam Locale compiles ICU MessageFormat JSON catalogs into generated, typed JavaScript. Each message becomes a function built on the platform `Intl` APIs, so `m.greeting({ name: 'Ada' })` is type-checked against the catalog and there is no runtime parser. The catalogs are the source of truth; everything the generator writes is derived from them.

Run every command from the project root with `npx nordbeam-locale ...` (or the package script). Prefer `--json`: it prints exactly one JSON document, so parse it instead of scraping text.

## 1. Understand the project

- `nordbeam-locale.config.json` holds `baseLocale` (default `en`), `catalogs` (default `messages`) and `outDir` (default `src/i18n`). Read it before guessing paths.
- `npx nordbeam-locale inspect --json` reports locales, per-catalog counts, whether generated output is fresh, and which framework integration is detected. `FILE_NOT_FOUND` means the project was never initialised: go to step 2.
- Catalogs are strict JSON, one file per locale named with a canonical BCP 47 tag (`en.json`, `pt-BR.json`). Nested objects give dotted IDs: `{"cart": {"total": "..."}}` is both `m.cart.total()` and `m['cart.total']()`.
- Inside `outDir`, the files listed in `.nordbeam-locale-manifest.json` (headed `Generated by Nordbeam Locale`) are generated. Scaffolds that `init` creates there (`client.ts`, `next.ts`, `provider.ts`, `routing.ts`, `vue.ts`, `svelte.ts`, `solid.ts`) are ordinary source you may edit.

## 2. First-time setup

```sh
npm install @nordbeam/locale                 # the runtime the framework adapters live in
npm install --save-dev nordbeam-locale       # the CLI, compiler and Vite plugin
npx nordbeam-locale init --framework <next|vite-react|tanstack-start|vue|svelte|solid>   # omit for plain TS/Node
```

Install first, at the same version: without a local install, `npx nordbeam-locale` downloads the latest release, which may not match the runtime in `package.json`. A plain TS/Node project that only imports the generated modules needs `nordbeam-locale` alone. Without `--framework`, init infers it from `package.json` (next, @tanstack/react-start, else vite plus vue, svelte, solid or React). Also available: `--catalogs <dir>`, `--base-locale <locale>`, `--out-dir <dir>`. Init creates what is missing and never replaces a file, so an existing `vite.config.ts`, `next.config.*` or `proxy.ts` is reported as preserved and you must wire it by hand. It also adds `i18n`, `i18n:watch` and `prebuild` scripts and seeds a starter `messages/en.json` (`greeting`, `items`) that you replace with the app's real base-language text.

## 3. The edit loop

1. Edit `messages/<locale>.json`: base locale first, then the other locales. Add a key with `npx nordbeam-locale extract --id cart.empty --message "Your cart is empty" --json` (writes the base catalog only), or edit the JSON directly.
2. `npx nordbeam-locale check --json` validates ICU syntax, IDs and cross-locale argument contracts without writing anything. Add `--strict` when translations must be complete: missing ones become `MISSING_MESSAGE` errors instead of `FALLBACK_MESSAGE` warnings.
3. `npx nordbeam-locale generate --json` compiles the typed modules. Plain `npx nordbeam-locale` does the same but rejects `--json`. The Vite plugin and `withNordbeamLocale` regenerate while a dev server runs; run it explicitly before type-checking or building anyway.
4. Run the app's type-check, tests or build. A type error on `m.something(...)` means the call and the catalog disagree: fix whichever is wrong, never cast it away.
5. `npx nordbeam-locale verify --json` before declaring the task done. It exits 0 only when `check` passes and the generated output is fresh and unedited. Output is tied to the mode it was generated in: `vite build` and `next build` regenerate it as production output, so after a build run `generate` and `verify` with the same `NODE_ENV` (for example both with `NODE_ENV=production`), or `generate` again right before `verify`.

`ok: false` or a non-zero exit is failure. Read `summary.byCode` for the shape of the problem, then each `errors[]` entry (`code`, `file`, `line`, `column`, `frame`, `fix`, `docs`). Run `npx nordbeam-locale explain <CODE> --json` for the cause and fix of any code. Lists are capped at 50 rows; narrow with `--only CODE[,CODE]` or `--limit all`, or use `--summary` for a compact answer. Exit codes, flags and MCP: [references/cli-agent-contract.md](references/cli-agent-contract.md).

## 4. Write messages

Messages are ICU MessageFormat strings. The shapes you need most:

```json
{
  "greeting": "Hello {name}!",
  "items": "{count, plural, =0 {Your basket is empty} one {# item} other {# items}}",
  "role": "{role, select, admin {Administrator} editor {Editor} other {Member}}",
  "total": "Total: {amount, number, ::currency/USD}",
  "due": "Due {date, date, medium}",
  "terms": "Read our <link>terms</link>.",
  "literal": "Use '{'braces'}' and don''t worry"
}
```

- Every `plural` and `select` needs an `other` branch. Inside a plural, `#` is the locale-formatted count; `{count}` prints the raw number.
- Quote literal `{`, `}` and `<` with apostrophes; write `''` for a literal apostrophe. Do not quote `#` outside a plural.
- Rich text uses XML-like tags; each tag becomes a typed callback argument. Keep the same tags in every translation.
- Put formatting in the catalog (`number`, `date`, `time`, `::currency/EUR`, `::compact-short`) so translators control word order. Pin `"timeZone"` in the config when server and browser output must agree.
- A translation must use exactly the base message's arguments and plural/select branches; extra or missing ones are reported (`UNKNOWN_ARGUMENT`, `MISSING_ARGUMENT`, `MISSING_PLURAL_CATEGORY`). Languages such as Arabic and Polish need more plural categories than English.
- Context for translators (where the text appears, what an argument holds, review rules) goes in the notes file the config names with `"notes"`, keyed like the catalog, never in the message text. Notes show as `@remarks` on hover and as `#.` comments in PO exports; `rename` moves them, and `UNKNOWN_NOTE` means a note's message is gone.
- Never build message text by concatenating fragments in code, and never use a computed key (`m[someVariable]`): static IDs keep the types and bundle pruning working.

Full syntax with verified output for each form: [references/icu-messages.md](references/icu-messages.md).

## 5. Call messages

Generated modules export `loadLocale(locale)` (resolves `{ locale, messages }`), `locales`, `baseLocale`, the types `Locale` and `Messages`, and `selectMessages(...ids)`. The usual call is `m.id(args)`; a message with no arguments takes none; the argument types come from the ICU shape (`string | number` for `{name}`, `number` for plural/number, `Date | number` for date/time, a literal union for `select`, callbacks for rich tags). Locale switching, loading states and SSR are framework adapters, not hand-rolled state: use the reference for the framework in use. Never keep the current locale in a module-global variable on the server; two concurrent requests must be able to render different locales.

## 6. Other tasks

- **Add a language**: create `messages/<locale>.json` with the translated keys, run `check --strict`, `generate`, then `verify`. Untranslated keys fall back to the base text. Add the locale to any switcher and, for Next.js, to the routing; right-to-left locales also need `dir` on the document.
- **Rename or remove a message**: `rename --id old --to new --regenerate --json` updates every catalog and recognisable source references. `prune --dry-run --json` only reports unreferenced IDs; delete them yourself after reviewing dynamic usage.
- **Translator hand-off**: `export --locale fr --out translations/fr.po`, then `import --locale fr --from translations/fr.po --dry-run --json` before importing without `--dry-run`.
- **Find text that was never translated**: `hardcoded --json` lists UI text in the source that is not a catalog message, with `file`, `line`, `text`, `confidence` and `reason`. `hardcoded --fix --json` previews replacing text with the catalog message that renders the same; `--extract` also adds new messages to the base catalog. Read `plan.skipped` before applying with `--write --regenerate`, then translate the new keys in the other locales. Mark text that must stay as written with a `// nordbeam-locale-ignore` comment.
- **How complete, used or large are the translations**: `report --json` for the numbers. When a person asks, offer `npx nordbeam-locale report --open`, which writes a local HTML page with coverage, unused messages, namespaces, scopes and catalog sizes.
- **Pseudo-locale for layout testing**: `pseudo --locale en-XA --dry-run --json`, then without `--dry-run`.
- **Tests**: `nordbeam-locale/testing` gives `createMessageTestHelpers<Messages>()`, and `messageIds`, `withMessages` and `compileMessages` for the messages a component test renders; see [references/node.md](references/node.md).
- **Production builds** must run with `NODE_ENV=production` (or `generate --production`); otherwise the output keeps development argument guards. `init` adds `"prebuild": "nordbeam-locale"`, not `prepare`.
- **MCP**: `claude mcp add nordbeam-locale -- npx nordbeam-locale mcp` serves check, generate, inspect and rename as tools.

## 7. Rules that prevent most mistakes

- Edit catalogs and application source only. Hand-edits to generated files are overwritten and make `verify` fail with `GENERATED_MODIFIED`; the fix is in the catalog, then `generate`.
- Import generated modules with the `.js` extension in Vite, Node and TypeScript projects (`./i18n/index.js`), exactly as the scaffolds do. Next.js scaffolds import sibling `.ts` sources without an extension; copy the scaffold style.
- Do not pass a loaded messages object or message functions from a Server Component to a Client Component. Pass the locale string.
- `selectMessages` shrinks bundles only under the Vite plugin. In Next.js use configured `scopes` for route-sized chunks. A scope can be computed from the files that render a part of the app (`{ "modules": [...] }`), and TanStack Start can load it for those routes (`staticData.i18nScope`).
- A new base-catalog key with no translation is not an error until `--strict`; do not hide `FALLBACK_MESSAGE` warnings by copying English into other locales unless asked.
- If a project already uses i18next, next-intl, react-intl, Lingui or similar and the user wants to move to Nordbeam, stop and use the `nordbeam-locale-migrate` skill instead of rewriting calls by hand.
